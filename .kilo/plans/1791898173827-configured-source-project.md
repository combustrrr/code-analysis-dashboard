# Configured source project and revision selection

## Goal

Extend the fixed-host dashboard so a user can inspect one of the three centrally configured source projects, select a branch, open PR, or full commit SHA, review the exact revision and scanner selection, then explicitly submit one read-only analysis request. Each accepted request is pinned to one immutable SHA. Scanner channels fan out from that SHA, while the service processes only one source-revision request globally at a time.

Related sign-in and authorization decisions remain in `.kilo/plans/1791898173827-dashboard-sign-in.md`.

## Confirmed decisions

- Execution host remains `combustrrr/code-analysis-dashboard`. The only source projects are:
  - `ARYDESTROYER/Kavach-AgenticSOC` (`1267340546`, preferred branch `Testing`)
  - `combustrrr/Agentic-Kibana` (`1278177697`, preferred branch `Testing`)
  - `combustrrr/code-analysis-dashboard` (`1360051890`, preferred branch `main`)
- Project profiles remain centrally managed and read-only in the dashboard. Preserve project-specific API/test configuration; align the same portable scanner baseline across all three profiles. Do not add arbitrary repositories, folder mapping, command editors, credential entry, or configuration PRs.
- Project selection and revision preview are read operations. GitHub `pull` permission can browse projects/reports; `push` is required only to submit a scan. `admin` remains for trusted registry maintenance.
- Scan triggers are manual only. Stop scheduled, push, and PR-event discovery from launching scans. Live branch/PR inventory reads and scheduled recovery of already accepted requests are allowed; recovery must never invent a scan request.
- No permanent/fixed Evaluation Mode SHA, branch lock, or one-dispatch budget. Each request resolves a fresh immutable SHA; this per-request pin is for reproducibility, not a frozen project target.
- A launch handles one configured project and one resolved source SHA. All selected scanner lanes consume that same SHA. One request may fan out to multiple lanes, but only one source-revision request may be active globally.
- Branch selection lists all current branches. PR selection lists all open PRs, including drafts and fork heads. Manual commit selection accepts any full 40-hex SHA GitHub resolves within the configured source repository; reachability from a current ref is not required.
- Require an explicit revision choice; do not preselect the preferred branch. Before queueing, show a review of the exact full SHA. For branch/PR selections, reject confirmation if the ref or PR head/base changed since preview; require refresh rather than silently retarget. Once accepted, process the pinned snapshot even if the ref later moves. Fail explicitly if the pinned object becomes inaccessible.
- Report identity deduplicates source-only evidence by configured project/repository identity, SHA, trusted tooling SHA, and profile digest. Preserve the original branch/PR/SHA selection as provenance. PR-context evidence is a separate overlay keyed by project, PR, head repository/SHA, base SHA, tooling, and profile; keep only the current overlay with the current repository report.
- Retain one current report per configured source repository. Replace it only after the first valid result for a new SHA is published; retain the previous report while queued/running and on failure before any valid new evidence. Remove superseded report assets only after the new manifest is committed. Keep bounded request/provenance metadata, not old full-SHA report history.
- Users choose scanner channels per run. Preselect the common portable baseline; vendor-backed lanes are opt-in. Disabled, deferred, unavailable, and not-applicable channels show their reason. Per-run selection never edits the central profile. Do not promise zero cost: GitHub Actions quotas and selected vendor services may incur usage.
- For the same project/SHA/tooling/profile, merge valid channel evidence across requests. A selected channel replaces its own prior channel evidence only after validated success; failed attempts remain visible without erasing its last valid same-SHA evidence. Never merge findings across SHAs. Use an explicit `NOT_SELECTED` status distinct from `NOT_APPLICABLE`, `DEFERRED`, and execution failure.
- Publish incrementally as each selected channel run completes. The report must distinguish requested, running, completed, failed, and not-selected channels; one successful channel must not imply full-project coverage. A new-SHA report can replace the prior report after its first valid channel result; if no valid result arrives, preserve the prior report and show the failed request separately.
- Matching retained channel evidence is reused by default; “Run again” explicitly forces the selected channels. Duplicate HTTP retries must be idempotent. If a matching request is already active/queued, do not create accidental duplicate work.
- Queue manual requests FIFO, with one active source-revision request globally. Selected channel workflows for that active SHA may fan out concurrently. Keep the current bounded queue limit (100); show queued/running state and position. Do not provide queue cancellation in this phase. A `202` means accepted/queued, never completed.
- No scanner findings, comments, checks, SARIF, commits, PRs, or other analysis feedback are written to any source, including self-analysis. Disable future native feedback for all three targets. Do not delete historical GitHub feedback as part of this work. Public Actions-artifact confidentiality remains a separate workstream.

## Implementation steps

1. **Make the project overview read-only and truthful.** Reuse the fixed three-entry registry and existing readiness/report APIs. Show project identity, current report SHA/time/status, and compact readiness summary with an expandable full channel list. Explain that `connected` identifies the same execution repository, not permission to publish findings. When the current branch/PR head differs from the sole retained report SHA, label the report as belonging to another revision; do not present it as current for the selected ref.

2. **Add live revision inventory and resolution preview.** Extend `/api/project-targets` to return full branch heads and open-PR metadata (title, draft flag, head repository/branch/SHA, base branch/SHA). If an individual PR head is unavailable, expose an incomplete-inventory warning/disabled item without silently claiming complete coverage or blocking usable branches. Add an authenticated resolve/preview contract for branch, PR, and manual SHA. Resolve commit metadata server-side, show the full SHA and PR context before confirmation, and revalidate the preview snapshot on final submission. Preserve the configured source repository ID and fork-head repository ID separately.

3. **Create an immutable, idempotent request envelope.** On confirmation, persist project ID, configured source identity, original selection, resolved head SHA, optional PR head/base context, requested channel IDs, tooling SHA, profile digest, actor, and idempotency key. Validate every channel against the trusted profile/catalog; reject arbitrary channel IDs, commands, repositories, malformed SHAs, stale previews, and insufficient write permissions. Keep commit SHA canonicalization lowercase while displaying the full value.

4. **Remove automatic scans and fixed evaluation gates.** Update Worker policy, `config/code-analysis/service.json`, trusted registry handling, and reconciliation so no push/PR/scheduled discovery can create scan work. Remove Kavach's Evaluation Mode branch/SHA/budget rejection. Configure one globally active revision request while allowing its selected channel lanes to run concurrently. Keep FIFO draining/recovery limited to explicit durable requests; quarantine or mark old automatic-discovery queue entries as superseded so they cannot run after cutover. Let already active runs finish and reconcile them; do not cancel them.

5. **Support run-level channel selection and incremental trusted publication.** Add explicit portable/vendor classification to the trusted scanner catalog; normalize the shared portable baseline across the three projects while preserving project-specific profile commands and current vendor configuration. Preselect applicable portable lanes, leave vendor lanes opt-in, and disable unsupported/deferred choices with reasons. Dispatch one isolated producer run per selected channel (or an equivalent completion-event design) with the same pinned SHA and request identity. Source jobs retain read-only checkout and no publication/vendor credentials. A trusted reconciler handles each lane's completion, verifies repository/SHA/tooling/profile/channel/run-attempt provenance, and atomically merges that channel into the current report. Keep the global request active until all selected lanes are terminal; only then drain the next request. Regenerate generated workflows 11 and 12 with `generate_source_workflow.py`.

6. **Implement current-report/cache semantics.** Store one current source-only result per configured repository/SHA/tooling/profile and one current PR overlay when applicable. Reuse matching channel evidence; run only missing selected channels unless the user explicitly chose “Run again.” For a same-SHA rerun, replace only the selected channel after valid evidence and retain other matching channels. For a different SHA, start a fresh report with unselected lanes marked `NOT_SELECTED`; never carry old-SHA findings forward. Keep the previous report visible until a validated new-SHA channel result is committed, then atomically replace the manifest and safely remove superseded full report assets. Scope publication-gate/completeness metrics to selected channels while separately showing selected coverage versus the configured baseline.

7. **Build the two-stage project/revision/channel UI.** Require a revision choice among Branch, Pull request, and Commit SHA. Show all open PRs including drafts/forks, with exact source and base provenance. Require a full SHA and server resolution for manual input. The review step shows project, original selector, exact SHA, PR context if any, selected channels/readiness, expected scope, and usage caveat; only the final confirmation queues work. Provide the portable-default channel selection, vendor opt-in, cache/reuse indication, explicit “Run again,” and incremental per-channel progress. Readers can inspect/preview; only writers see submission controls. No cancel control is present.

8. **Update operational documentation and cut over safely.** Update `README.md`, `docs/HANDOFF.md`, `docs/MIGRATION.md`, `docs/current/AUTHENTICATED_LAUNCHING.md`, `docs/current/MONITORING_UI.md`, and the relevant operations guide to remove claims of hourly branch/PR scans, two concurrent analyses, fixed Evaluation Mode, per-ref report retention, and one-click launch. Document FIFO/manual-only semantics, cache/overlay keys, channel statuses, no source writes, usage caveat, and the remaining public-artifact privacy limitation. Deploy the Worker/report reader and trusted workflows before exposing the new UI; retain backward reading of the existing manifest until the first valid v2 publication. Do not delete the existing report until the replacement manifest is committed.

## Validation

- Worker/API tests: fixed project allowlist and role checks; branches, open draft/fork PRs, full/historical SHA; stale preview rejection; exact request pinning; all three projects without an Evaluation Mode exception; idempotency; FIFO queue, one active revision, queue limit, no cancellation; no automatic discovery dispatch; no source-feedback calls.
- Service/report tests: per-channel producer provenance; incremental atomic publication; same-SHA merge and selected-channel replacement; profile/tooling invalidation; no cross-SHA evidence; PR overlay separation; `NOT_SELECTED` versus failure/deferral/not-applicable; one-current-report replacement and preservation on failure/capacity errors.
- Workflow audit: only explicit user request creates scanner runs; completion/recovery only processes accepted intents; source jobs have no publication/vendor credentials and no feedback permissions; each selected lane checks out exactly the same pinned SHA.
- UI checks: no default revision, explicit preview then confirmation, visible SHA and PR provenance, portable defaults/vendor opt-in, truthful partial status, last report versus current request, queue position, reader/writer behavior, cache hit and forced rerun.
- Run service tests, launcher tests (`node --test analysis-launcher/*.test.mjs`), workflow audit (`python -m scripts.code_analysis.audit_workflows`), deployment tests, and relevant UI build/Playwright checks. Update current operational state after implementation. Do not perform a production scan or deployment as part of local validation without separate authorization.

## Explicitly out of scope

- User-facing source/profile setup or arbitrary repository onboarding.
- Source-repository writes, PR creation/update/comment, GitHub-native feedback, or historical feedback deletion.
- Automatic push/PR/cron scanning; live ref inventory reads remain allowed.
- Changing the fixed execution host or moving scanner runtime into source repositories.
- Guaranteeing zero Actions/vendor cost or making public Actions artifacts private. The latter needs its own security/storage design.
